### Дополнение после проверки на рабочей базе (21.10.2026)

Простыми словами: новая версия проверена на копии настоящей базы. Свежий прайс импортируется так же, как раньше. Урезанный прайс больше ничего не стирает, а старая версия на нём стирала поля у всех товаров. По итогам проверки исправлены две мелочи.

- Индекс `price_snapshot_items(article, snapshot_id, id)` создаётся при импорте прайса (`CREATE INDEX IF NOT EXISTS`). На копии рабочей базы чтение всех 11 802 товаров без индекса не закончилось и за 10 минут, а с индексом заняло 25 секунд. Частично закрывает OPT-04. В базе индекс появится при следующем импорте прайса.
- Прайс без колонок цен больше не считается базой для сравнения: `latest_snapshot_id` выбирает последний снимок с ценами. В таком прайсе отсутствующая цена не считается изменением цены. Иначе после урезанного файла счётчики «новых артикулов» и «изменений цены» завышались.

## 3. Прайс: парсинг и обновление базы

### PRI-01 — неверное разрешение путей листов XLSX · P1 · В

**Код:** `price_importer.py:175`, строка 195: `sheet_path = "xl/" + relmap[rid]`.

**Сценарий:** книга содержит `Target="/xl/worksheets/sheet1.xml"`. Получается несуществующий путь `xl//xl/worksheets/sheet1.xml` и импорт прекращается. Воспроизведено на книге со всеми четырьмя ожидаемыми листами, созданной openpyxl.

**Исправление:** разрешать OPC-пути относительно `xl/workbook.xml`, поддержать относительные и абсолютные package paths, нормализовать их как POSIX-пути внутри ZIP. Проверять наличие relation, тип связи и элемента архива; выдавать сообщение с именем листа. Не использовать Windows `Path` для путей внутри ZIP.

**Приёмка:** один и тот же набор данных читается из исходного Excel, XLSX после openpyxl и XLSM; тесты покрывают `worksheets/...`, `/xl/worksheets/...`, shared/inline strings, отсутствующую связь и повреждённый ZIP. Нельзя подменять `read_sheet_rows` в этих тестах.

### PRI-02 — неполный прайс молча стирает поля товаров · P1 · В

**Статус:** исправлено 21.10.2026 во втором наборе; остаток указан в таблице второго набора выше.

**Код:** `price_importer.py:214`, `:315`, `:319`.

Валидация требует только `Артикул` и `Наименование`; отсутствующая колонка возвращается как `""`. UPSERT безусловно заменяет `series_name`, `unit`, группу, тип и другие поля. Воспроизведено: товар с `unit='шт', series_name='NXB'` после импорта строки только с артикулом и наименованием получает `('', '')`.

**Исправление:** различать отсутствующую колонку, пустое значение и намеренное очищение. Отсутствие колонки не должно стирать поле. Для полного официального прайса проверять согласованный профиль заголовков до изменения БД; для поддерживаемого частичного файла обновлять только присутствующие поля. Не запрещать законные обновления статусов/акций простым правилом «никогда не записывать пустоту».

Нужна канонизация заголовков: BOM, NBSP, переносы, повторные пробелы, согласованные варианты `е/ё`, обозначений объёма и единиц. Сейчас `strip()` не устраняет внутренние расхождения, например `Вес нетто…` против ожидаемого `Вес  нетто…`. После канонизации выявлять дубли, а не молча схлопывать их через `dict(zip(...))`.

**Приёмка:** частичный файл сохраняет прежние поля; перестановка колонок и разрешённые варианты заголовков не меняют результат; неизвестные/дублирующиеся значимые колонки отражаются в диагностике; пустое имя не стирает корректное без явной политики.

### PRI-03 — текстовые числа превращаются в неправильный вес/объём · P1 · В

**Статус:** исправлено 21.10.2026 во втором наборе; остаток указан в таблице второго набора выше.

**Код:** `price_importer.py:148`, `:319`; `db.py:115` и остальные `CAST(... AS REAL)`.

Импорт сохраняет числовой текст как есть, а чтение поручено SQLite. Проверено: `CAST('0,125' AS REAL)=0`, `CAST('1 234,5' AS REAL)=1`, `CAST('нет' AS REAL)=0`. Так можно получить правдоподобное, но неверное заполнение. Это относится к текстовым ячейкам; числовые XML-ячейки текущего официального прайса не следует объявлять повреждёнными.

**Исправление:** общий строгий разбор чисел с запятой/точкой и разделителями разрядов, проверкой конечности и допустимости для конкретного поля. Хранить исходное значение и отдельно нормализованное; некорректное значение не превращать в ноль. Учесть уже существующие текстовые данные при чтении/миграции. Артикулы и коды не проводить через float; унифицировать нормализацию артикулов между импортерами и filler, сохраняя текстовые ведущие нули.

**Приёмка:** `0,125 → 0.125`, `1 234,5 → 1234.5`; `нет`, ошибки формул, `NaN/Inf` не записываются как размер/вес. Числовой артикул и соответствующий артикул шаблона сопоставляются; текст `00123` остаётся `00123`.

### PRI-04 — дата снимка зависит от переименования файла, повторы раздувают историю · P2 · К

**Код:** `price_importer.py:132`, `:240`, `:289`, `:493`; `etim_importer.py:511`, `:598`.

Повторное скачивание добавляет `_1` к имени, а `snapshot_date_from_filename` переносит суффикс в «дату». Каждый повторный импорт создаёт снимок/ETIM-строки. Дубли артикулов в прайсе не выявляются; сравнение цен через JOIN может умножать число изменений при дублях в обоих снимках. Цены `100` и `100.00` сравниваются как разные строки.

**Исправление:** дата из проверенных метаданных или строгого шаблона имени, отдельно время загрузки/импорта. SHA-256 и идентификация успешно применённого содержимого в журнале импорта; повтор возвращает понятный результат. Сохранить возможность намеренного повторного применения после восстановления БД. Дубли идентичных строк схлопывать, противоречивые показывать; сравнивать нормализованные цены.

**Приёмка:** повтор одного содержимого не создаёт неявных дублей, `_1` не становится частью даты; счётчики корректны на дублях; старые снимки остаются доступными.

## 4. Поиск и скачивание прайса

### NET-01 — HTML и незавершённый файл выдаются за XLSX · P1 · В

**Код:** `price_importer.py:104`; `app.py:161` (`PriceImportWorker`).

Файл сразу создаётся под окончательным именем. Воспроизведено: HTTP-ответ с HTML сохраняется как `price.xlsx`; обрыв чтения оставляет `broken.xlsx` с 10 байтами. ZIP/структура Excel проверяются лишь позднее парсером. GUI объединяет скачивание и импорт: если загрузка успешна, а импорт упал, путь к скачанному файлу не поступает в `on_price_import_done`.

**Исправление:** загрузка в уникальный `.part` в целевой папке; проверка размера и фактически полученных байтов, допустимого содержимого и структуры XLSX/XLSM; публикация окончательного имени только после проверки. Чистить временный файл при ошибке. Сохранять отдельные результаты этапов «скачано» и «импортировано», чтобы повторить импорт без загрузки. MIME использовать как дополнительную проверку, не отклоняя корректный `application/octet-stream`.

**Приёмка:** HTML, обрыв, timeout и битый ZIP не оставляют готовый `.xlsx`; предыдущее скачивание не повреждается; при ошибке импорта валидный скачанный файл доступен пользователю.

### NET-02 — имя из HTTP-заголовка может выйти за папку загрузки · P1 · В/К

**Код:** `price_importer.py:118` и `downloads_dir / filename` в `:104`.

Проверено: `filename_from_response(..., 'attachment; filename="../outside.xlsx"')` возвращает `../outside.xlsx`. Склеивание допускает запись за пределами downloads; абсолютное имя также не фильтруется. Это дефект обработки внешнего имени, а не утверждение о вредоносности текущего сайта. Windows-имена с запрещёнными символами дают обычный сбой скачивания.

**Исправление:** корректно разобрать `filename*`/`filename`, декодировать имя, оставить безопасное имя файла с учётом обоих разделителей, Windows reserved names и символов. Проверить принадлежность итогового пути каталогу загрузки. Имя из конечного URL использовать как fallback. Разрешать поддерживаемые сетевые схемы; проверять redirects, сохраняя HTTPS по умолчанию.

**Приёмка:** `../`, `..\`, абсолютные пути, `%2F`, `CON`, двоеточие, кириллица и `filename*=UTF-8''...` не вызывают запись вне папки; имя уникально и пригодно для Windows.

### NET-03 — поиск «свежего» файла привязан к написанию и порядку ссылок · P2 · К

**Код:** `price_importer.py:78`.

Проверяется регистрозависимая подстрока `Price-list-CHINT`; подходящая ссылка возвращается первой, без сравнения дат. Относительный URL разрешается относительно исходной страницы, а не `response.geturl()` после redirect. Работоспособность текущей страницы проверена, отказ при изменении страницы — отдельный сценарий.

**Исправление:** нормализовать путь/название, собирать кандидатов, учитывать тип оборудования и достоверную дату; разрешать ссылки относительно конечного URL. Сохранять ручной ввод ссылки и локальный импорт. Добавить ограниченные повторы только временных сетевых ошибок, прогресс, отдельные сообщения для DNS/TLS/HTTP/разбора; TLS-проверку не отключать.

**Приёмка:** HTML-фикстуры с query string, разным регистром, несколькими датами, относительной ссылкой и redirect; сетевые ошибки тестировать без зависимости от доступности сайта. В логах не сохранять секреты из query-параметров.

## 5. SQLite и корректность чтения

### DB-01 — соединения остаются открыты после выхода из `with` · P1 · В

**Код:** `db.py:57`, `:81`; `etim_importer.py:598`, `:673`.

В этих местах `with connect(...) as conn` управляет транзакцией, но не закрывает SQLite connection. В диагностике после ETIM Windows выдал `WinError 32` при удалении временной `db.sqlite`; файл освободился после завершения процесса. Обычные тесты backup проходят, поскольку там уже используется `closing`.

**Исправление:** `with closing(connect_database(...)) as conn, conn:` для записей, `closing` для чтения; явный владелец и срок жизни каждого соединения. Аналогично закрывать read-only workbooks через `finally` в `manual_values.py:129`, `app.py:1300/:1350`, а также книги filler/analyzer на всех путях выхода.

**Приёмка:** сразу после статистики, fetch, ETIM, решений и исключений БД/входной XLSX переименовываются на Windows без `gc.collect()` и перезапуска приложения. Отдельно проверить отсутствие блокировок после неудачного отчёта.

### DB-02 — restore/copy не защищены от других процессов и чужой схемы · P1 · К/Р

**Код:** `db_utils.py:47`, `:92`, `:122`; `app.py:792` (`copy_db_to_workspace`).

`restore_sqlite_backup` удаляет `-wal/-shm` перед заменой файла, не обеспечив отсутствие внешних соединений. Глобальная блокировка worker защищает только одно окно программы. `copy_sqlite_database` может заменить уже существующую рабочую БД без safety backup. `integrity_check` проверяет структуру SQLite, но не совместимость таблиц приложения; исправная чужая SQLite может пройти restore и затем сломать работу. Потеря данных при внешнем конкурентном доступе не воспроизводилась на рабочей БД.

**Исправление:** сначала DB-01; единый протокол владения БД для GUI/CLI, запрет файловой замены при активных соединениях, безопасная обработка WAL через SQLite, а не безусловное удаление sidecars. Перед заменой проверять совместимость схемы; при copy поверх существующей БД создавать safety backup, same-file делать no-op. Внешние приложения, не соблюдающие lock-файл, учитывать отдельно: один lock-файл не доказывает безопасность `os.replace`.

**Приёмка:** rollback-journal и WAL; открытое второе соединение/второй процесс; отказ файловой замены; same-file; повреждённый и чужой backup. При отказе исходные данные и WAL сохраняются.

### DB-03 — пустые строки подавляют fallback; производитель используется как единица · P2 · К

**Код:** `db.py:93`, `:94`, `:106`, подзапросы class81/ОКПД2.

`COALESCE` пропускает NULL, но принимает `''`. Поэтому пустое имя/класс из `ipro_goods` скрывает непустой источник ниже по приоритету; пустой `okpd2_9` скрывает `okpd2_6`. При NULL в `p.unit` используется `ig.manufacturer`, что семантически не является единицей измерения.

**Исправление:** `NULLIF(TRIM(...), '')` для текстовых fallback и отдельный корректный источник единицы. Не менять приоритет непустых источников без проверки предметного смысла. Зафиксировать его тестами, включая приоритет атрибутов по confidence и id.

**Приёмка:** таблица случаев NULL/пусто/пробелы/непусто для имени, класса, кодов и единицы. Вес единицы не подменяется весом упаковки.

### DB-04 — нет предварительной проверки поддерживаемой схемы · P2 · К

**Код:** `db.py:57/:81`, `price_importer.py:493`, `etim_importer.py:267`.

Чтение требует множество таблиц и колонок; цена не создаёт схему, ETIM создаёт только свою часть. Выбор существующего файла не означает его совместимость. Старый/неполный файл приводит к `no such table/column`; расширение не решает проблему. Программа сейчас требует готовую базу, поэтому отсутствие создания новой БД само по себе не объявляется багом.

**Исправление:** read-only preflight с перечнем обязательных объектов для операции, понятная ошибка версии/схемы; затем только необходимые версионированные миграции с backup. Не создавать пустые заглушки таблиц для сокрытия несовместимости.

**Приёмка:** текущая поддерживаемая БД работает без изменений данных; старый/неподдерживаемый файл отклоняется до записи; ошибки миграции обратимы.

## 6. ETIM и отчёты конфликтов

### ETI-01 — габариты угадываются и подавляют точные колонки · P1 · В

**Статус:** исправлено 21.10.2026 во втором наборе; остаток указан в таблице второго набора выше.

**Код:** `etim_importer.py:96/:109/:141/:156/:207`.

Общий размер всегда интерпретируется как Ш×В×Д. Воспроизведено: колонка `Габаритные размеры ДхШхВ, мм` со значением `100x200x300` и отдельными точными колонками 100/200/300 даёт ширину 100, высоту 200, длину 300. Точные колонки пропускаются через `if key in dimensions: continue`. Для `Габаритная длина, см` значение 12 воспринимается как 12 мм. Поиск первого числа также не различает диапазон, предел и размер.

**Исправление:** приоритет независимым явно обозначенным измерениям; распознавать порядок общей цепочки по заголовку и единицы в заголовке/значении. Неоднозначные цепочки, диапазоны, отрицательные/нечисловые значения отправлять в отчёт, не угадывать. Не менять ранее разрешённые габариты автоматически.

**Приёмка:** Д×Ш×В, Ш×В×Г, мм/см/м, десятичная запятая, явные колонки вместе с цепочкой, отрицательные значения, диапазоны и цепочки из 2/4 чисел. Для однозначных старых файлов результат сохраняется.

### ETI-02 — первое совпадение артикула мешает дочитать характеристики · P1 · В

**Код:** `etim_importer.py:207`.

Артикул добавляется в `found` после первого подходящего совпадения, даже без габаритов. Последующие строки/листы игнорируются; после нахождения всех артикулов сканирование заканчивается. Воспроизведено: первый лист содержит только наименование, второй — длину; результат `dimensions={}`. Поиск по всем ячейкам с заголовком, содержащим «артикул», также может принять артикул аналога за основной.

**Исправление:** сначала определить структурные колонки основного артикула; собирать данные из всех релевантных листов, объединять непересекающиеся атрибуты. Конфликтующие значения не выбирать молча. Повторяющиеся заголовки и неизвестные артикулы показывать в отчёте. Нулевое совпадение не обозначать как обычный успешный импорт.

**Приёмка:** краткий лист перед подробным не теряет данные; порядок листов не меняет итог; аналог не становится основным товаром; конфликт повторных строк прозрачен.

### ETI-03 — старый или чужой отчёт перезаписывает новые данные · P1 · В

**Статус:** исправлено 21.10.2026 во втором наборе; остаток указан в таблице второго набора выше.

**Код:** `etim_importer.py:673`.

Колонка `Сейчас в базе` не проверяется, обязательны только решение/артикул/поле/новое значение. Проверено: отчёт содержит старое 100 и предложение 200; база уже содержит 150; применение записывает 200. Разрешён произвольный артикул, значения `NaN/Inf` не фильтруются, принадлежность отчёта базе/импорту не проверяется.

**Исправление:** compare-and-swap по исходному значению в одной транзакции; проверка товара, конечного допустимого числа и уникальности решения. Для новых отчётов — версия, ID базы/импорта и связь с сохранёнными исходными конфликтами; редактируемый Excel содержит решения, а предложенное значение сверяется с источником. Повтор уже принятого решения — явный no-op.

**Совместимость:** не отклонять все старые отчёты автоматически только из-за отсутствия нового `_meta`. Предусмотреть проверяемый режим для старого формата со сверкой исходного значения/источника; если доказать принадлежность нельзя — предложить пересоздать отчёт, сохранив файл и возможность перенести решения. Это ограничение записи защищает данные, не должно молча уничтожать прежний workflow.

**Приёмка:** база 150 остаётся 150 при отчёте 100→200; чужой товар/БД, изменённое предложение, дубли, `NaN/Inf` не применяются; остальные корректные строки получают однозначный результат согласно выбранной политике транзакции.

### ETI-04 — ошибка отчёта скрывает уже завершённую запись · P1 · В

**Код:** `etim_importer.py:598` (commit на 642, отчёт после него); `price_importer.py:493` (commit до статистики); `manual_values.py:129` (JSON до отчёта).

Воспроизведено: при `PermissionError` в `write_etim_report` функция сообщает исключение, но в БД уже есть импорт и атрибут. Пользователь может повторить операцию, получив дубли. В прайсе аналогичный разрыв есть между commit и расчётом результата. ETIM также создаёт таблицы до проверки содержимого книги.

**Исправление:** preflight входного файла и места результата до записи; явный результат `committed_with_report_error` при сбое публикации после commit, с путём backup и повторным формированием отчёта без импорта. Расчёт обязательных итогов выполнять до commit либо явно отделять от успешной записи. Не обещать одну атомарную транзакцию SQLite+файловая система: нужна последовательность состояний и восстановление после каждого сбоя.

**Приёмка:** диск заполнен/отчёт открыт/отказ rename до и после commit; интерфейс достоверно сообщает, менялась ли БД/JSON; отчёт можно восстановить без дублирования данных.

## 7. Заполнение, ручные значения и маппинг

### FIL-01 — EMPTY_ONLY перезаписывает числовой ноль · P1 · В

`cell_text` использует `value or ''`; значения `0` и `False` считаются пустыми. Воспроизведено на реальном XLSX: исходный вес `0` заменяется на `12` из ProductRecord.

### FIL-02 — для неизвестного товара красным отмечаются заполненные поля · P2 · К

**Исправление:** подсвечивать только действительно пустые обязательные ячейки, отдельно учитывать неизвестный артикул; менять необходимые свойства стиля с сохранением остальных. При повторном заполнении отслеживать собственную подсветку, чтобы заполненные поля не оставались ошибочно красными.

**Приёмка:** неизвестный товар с уже заполненным названием сохраняет значение и оформление; счётчик соответствует пустым обязательным полям.

### FIL-03 — ручное значение сохраняется, но не применяется для отсутствующего товара · P2 · К

Предпочтительно первое, поскольку ручной workflow уже принимает такие значения. Не создавать автоматически товар в БД.

**Приёмка:** сохранённый override неизвестного артикула заполняет пустую ячейку XLSX/CSV, остальные отсутствующие данные остаются незаполненными.

### FIL-04 — сохранение результатов не атомарно; XML-расширения требуют проверки · P2 · К/Р

**Код:** `filler.py:300/:442/:450/:674`; функции создания отчётов в analyzer/manual/ETIM.

Выходные книги/CSV пишутся сразу по итоговому пути; имена имеют точность до секунды и могут совпасть при повторном быстром или параллельном CLI-запуске. `preserve_worksheet_dropdowns` переносит XML и заменяет архив, пока output ZIP ещё открыт; перенос может стать копированием между томами. Простой локальный XLSX с dropdown сохранился успешно — постоянный отказ этой функции не подтверждён. Сложные x14-валидации, связанные ресурсы и порядок XML-элементов требуют проверки в Excel.

**Исправление:** уникальный staging-файл рядом с результатом; закрыть все архивы до замены; проверить архив, связи и наличие VBA, затем публиковать. Файл и отчёт связывать идентификатором операции. Не расширять вмешательство в XML без регрессионных фикстур.

**Приёмка:** сбой на сохранении не повреждает прежний результат; два запуска не перетирают файлы. Обычные и x14 dropdown, именованные диапазоны, стили, формулы, объединения и VBA открываются в Excel без восстановления содержимого.

### MAN-01 — возврат значения к базе не снимает старый override · P2 · К

**Код:** `manual_values.py:89/:129`.

Если сохранён override 20, а пользователь возвращает ячейку к значению БД 10, импорт пропускает её как равную БД. Старое 20 остаётся в JSON и снова применяется к пустому шаблону. Удаление значения в Excel также не удаляет override.

**Исправление:** явное действие «вернуть к базе/удалить ручное значение» с отчётом изменения. Не трактовать любую пустую ячейку как команду массового удаления. Сохранить чтение версии 1 JSON; сравнивать импортируемое значение также с существующим override, выявлять противоречивые дубли в книге.

**Приёмка:** после явного сброса применяется 10 из базы; простая пустая ячейка не удаляет сохранённое значение; повторный импорт без изменений не объявляет каждую строку новой.

### MAP-01 — отклонённое ранее утверждённое правило продолжает работать · P2 · В

**Код:** `mapping_rules.py:149/:226`.

`add_rejected_class_rule` добавляет запрет, но не удаляет источник из утверждённых и `source_attributes_for` не фильтрует запреты. Проверено: approve → reject → `source_attributes_for` по-прежнему возвращает источник. Сценарий возможен, в частности, при повторном открытии старого отчёта кандидатов.

**Исправление:** согласовать approve/reject в обе стороны, определить единственный эффективный набор правил. Не удалять другие утверждённые источники того же поля. Добавить валидацию элементов JSON, поскольку `load_attribute_rules` без проверки вызывает `.get()` у каждого элемента.

**Приёмка:** approve→reject прекращает применение источника, reject→approve возвращает его; повторные действия идемпотентны; повреждённая запись даёт понятную ошибку.

### MAP-02 — изменение правил может не отразиться или попасть в середину операции · P2 · К/Р

**Код:** `mapping_rules.py:205`; `app.py:1466/:1488`.

Кэш утверждённых правил привязан только к тексту пути, поэтому внешнее изменение файла не инвалидирует его. Кнопки правил доступны во время worker; сохранение сбрасывает кэш и разные строки одной операции могут использовать разные версии правил.

**Исправление:** загрузить и валидировать неизменяемый снимок правил на начало операции, учитывать версию/mtime/hash при следующем запуске. Все решения в одном результате должны происходить из одного набора правил. JSON read-modify-write разных процессов защищать отдельно от атомарного rename.

**Приёмка:** внешнее изменение подхватывается следующей операцией; текущая операция сохраняет один набор правил; два сохранения не теряют изменения друг друга.

### MAP-03 — часть кандидатов не доходит до пользователя · P2 · К

**Код:** `analyzer.py:201/:441`; `app.py:1350`.

Анализ учитывает только `candidates[0]`. Если для поля есть хотя бы один approved source, `write_mapping_report` не пишет новые кандидаты в лист «Правила», даже если approved source не покрывает часть товаров. GUI читает fallback «Выбор источника» лишь когда обычных кандидатов нет вообще, поэтому частичный набор скрывает остальные.

**Исправление:** учитывать несколько кандидатов с отдельным покрытием и примерами; сохранять кандидатов для непокрытой части поля; объединять оба источника GUI с удалением дублей. Самостоятельное автоматическое утверждение не вводить.

**Приёмка:** частично утверждённое поле и второе неутверждённое поле одновременно показывают все релевантные предложения; отклонённые источники скрыты. Анализ явно объясняет, что считает покрытие из БД, либо учитывает существующие ячейки и manual overrides так же, как filler.

## 8. GUI, CLI и конфигурация

### GUI-01 — после перезапуска нельзя выбрать старый ETIM-отчёт через кнопку · P2 · К

**Код:** `app.py:311`, `:1031` (`run_etim_import`), `:1050` (`apply_etim_decisions`).

Ветка выбора недоступна обычным нажатием кнопки. При наличии last-report нельзя выбрать другой отчёт через этот же обработчик.

**Исправление:** разрешить выбор существующего отчёта вне активной операции; отделить выбранный файл от последнего созданного. При смене БД показывать принадлежность отчёта и применять проверки ETI-03.

**Приёмка:** после перезапуска пользователь выбирает сохранённый отчёт; может переключиться на другой; во время записи запуск блокируется.

### GUI-02 — не определено закрытие приложения при работающем QThread · P1 · Р

**Код:** `app.py:321/:342/:1594`, отсутствует `closeEvent`.

Сильная ссылка на worker уже есть, но нет протокола ожидания/завершения при выходе. Закрытие последнего окна заканчивает event loop; работающий поток может оборваться при завершении процесса. Аварийный выход во время записи не запускался на пользовательских данных.

**Исправление:** обработать закрытие окна, дождаться безопасной границы операции или кооперативно отменить этап загрузки/разбора. Не использовать `QThread.terminate()` в транзакции. Освобождать worker после `finished`, обновлять GUI в главном потоке.

**Приёмка:** закрытие окна во время загрузки, ETIM, commit и сохранения отчёта не оставляет неизвестного результата; завершение/отмена не повреждает БД и готовые файлы.

### GUI-03 — пустые пути проходят проверку; часть ошибок GUI не обработана · P2 · К

**Код:** `app.py:792`, `:980` (`validated_db_path`), `:1076` (`validated_paths`), обработчики выбора папки и сохранения правил.

`Path('')` означает текущую директорию, а `exists()` возвращает True. Затем вместо «выберите файл» появляется техническая ошибка SQLite/ZIP. Copy, некоторые сохранения config/rules и создание папок не имеют такого же перехвата ошибок, как worker. Статистика, backup/restore/copy выполняются синхронно в UI и могут надолго его блокировать.

**Исправление:** проверять исходную непустую строку, затем `is_file()` и совместимость формата; единую обработку ошибок файловой системы использовать во всех слотах. Длительные операции переносить в существующий контролируемый worker; сохранять параметры операции на момент запуска и не путать их с изменёнными полями UI.

**Приёмка:** пустой путь, папка вместо файла, read-only каталог, заблокированная БД дают короткую русскую ошибку; UI остаётся отзывчивым.

### CFG-01 — валидный JSON неправильного типа ломает старт · P2 · В

**Приёмка:** object/list/null/число, битый JSON и недоступный файл не приводят к необработанному падению; корректные старые настройки читаются.

### CLI-01 — режим статистики без шаблона заканчивается ошибкой аргументов · P2 · К

**Код:** `cli.py:109/:123`.

**Приёмка:** stats-only возвращает 0; ошибки аргументов — ненулевой код до записи; поведение каждой допустимой комбинации покрыто CLI-тестом.

| Excel | открытие в Excel без repair; dropdown обычный/x14; стили/формулы/объединения; именованные диапазоны; VBA; файл открыт другим процессом |
| Правила/ручные данные | approve→reject→approve; несколько источников; внешний JSON-update; массовое сохранение; дубли; явное снятие override; старый JSON v1 |
| GUI/CLI | двойной запуск; завершение с ошибкой; закрытие окна во время работы; смена путей; выбор старого отчёта; stats-only; неверные аргументы; недоступная папка |
| Сборка | исходники и EXE одной версии; ресурс rules включён; запуск без установленного Python; кириллица/пробелы в путях |

## 13. Условия сохранения существующего функционала

1. Не менять форматы файлов и сигнатуры GUI/CLI без необходимости; старые JSON и backup должны оставаться читаемыми.
2. Не переписывать непустые ячейки, включая 0/False, и не исправлять исторические данные автоматически по новым эвристикам.
3. Сохранить загрузку по URL, локальный импорт, четыре текущих листа прайса, ETIM, CSV/XLSX/XLSM, ручные дополнения и ручной выбор маппинга.
4. Не делать необязательные листы прайса обязательными сверх текущего контракта и не считать их отсутствие нормой без согласованного профиля: сначала диагностировать структуру. Основной лист и валидные данные остаются обязательными.
5. Сохранить разделение штучных/минимальных/транспортных веса и объёма, точность значений и приоритет подтверждённых источников.
6. Не удалять существующие товары/снимки/правила как часть «оптимизации»; любые миграции выполнять на копии и с проверенным backup.
7. Исправление считается готовым после теста исходного сбоя и успешной регрессии затронутых рабочих сценариев, а не только после прохождения прежних 9 тестов.
